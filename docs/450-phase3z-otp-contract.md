## Test interpretation and proposed expiry contract

Four cohorts retain UTC/UTC,UTC/+06,Manila/+08 and add Manila/UTC. Actual direct FPM requests test fresh optional OTP and standard authentication. Native tests call the unchanged service for each of reset_password,verify_email,2fa, with stable clocks, changed PHP timezone after generation, and changed DB timezone after generation. SET SESSION timestamp advances or rewinds only the owned verification connection; PHP time is not changed. These are controlled database-clock experiments, not a claim of waiting601 seconds or extending a real PHP login intent.

At each stored expiry the native service is tested one second before, exactly at, and one second after. A fourth point is generation+601 seconds. Wall strings are independently converted back to epochs by the reporter. All known adverse mismatches remain in evidence.

Proposed shared **persisted-code** contract for separate review: lifetime600 seconds/default configured OTP_EXPIRY on one authoritative DB epoch; valid only strictly before expiry, unused and matching uid/action; at expiry reject. Preserve existing action bindings and independent PHP intent/token gates. Do not silently harmonize PHP session equality boundaries or marker TTL: those are separate policy decisions. Guarantee depends on a stable/synchronized DB clock; clock steps remain operational risk.

## Options requiring separate authorization

| Option | Behavior and guarantees | Compatibility / affected surfaces | Risks and review gates |
|---|---|---|---|
| A. Explicit application + connection UTC | Existing PHP date() and DB NOW agree only when every PHP entry point and DB connection uses UTC | `config.php` or documented ini/bootstrap; `database/config/db.php` connection init; CLI/FPM/worker startup and operations checks; no required column migration | Broad convention affects all timestamps, not OTP alone. Existing naive DATETIME cannot safely be reinterpreted. UTC rollout must address all writers/readers and independent external jobs; reconnect path too. Fail closed or alert on mismatch requires explicit availability/security choice |
| B. Consistent DB clock | Generate persisted expiry with DB `DATE_ADD(NOW(),INTERVAL configuredTTL SECOND)` and verify/count/purge under stable agreed DB clock | Minimum application implementation surface `security/forgot-password/OtpService.php`; tests; deployment clock/session policy; AuthService/API outputs unchanged | Fixes stable mismatches if same zone persists, but a zone change between generation/verification still reinterprets DATETIME. DB-only wall time without invariant is insufficient. Transactions, delivery and single-use race must not be casually changed in same patch |
| C. Explicit normalized representation | Epoch expiry/created/used plus DB epoch comparisons, or explicitly UTC DATETIME with UTC_TIMESTAMP on every operation | Shared service; additive reviewed schema migration if epoch columns; compatibility/version contract for old/new writers/readers; migration runner/runtime ensureTable coordination | Epoch representation resists connection-zone changes but requires migration/dual-writer compatibility. Existing DATETIME has no provenance, cannot infer original timezone. UTC DATETIME avoids column addition but mixed old writers remain ambiguous. More implementation and rollback complexity |

**Recommendation for review, not implementation:** prefer narrowly scoped option B with explicitly UTC OTP expressions (`UTC_TIMESTAMP()` for expiry/created/used generation, verification, count and purge), avoiding a global application-clock change. All OTP operations must share the convention; plain NOW-only B does not survive connection timezone changes. This is optionB's DB clock combined with optionC's explicitly UTC representation. Keep columns DATETIME, configured TTL and current strict DB expiry semantics. Target application file: `security/forgot-password/OtpService.php`; focused tests, fixtures, contract docs and operations evidence also change. No AuthService/API/middleware/session/ordinary-login/marker policy changes proposed. No automatic deployment configuration change.

### Required transition decision before any correction

Existing records cannot be distinguished as UTC,Manila or another local zone. **Do not convert existing DATETIME using the current session zone.** A reviewed rollout must choose either (1) explicitly invalidate outstanding persisted OTP rows at a coordinated writer cutover, accepting forced re-request, or (2) versioned records/writers and bounded legacy handling whose old timezone provenance is actually known. Waiting600s alone is insufficient: reverse-mismatched rows may compare valid for29400s, and their origin is untrusted. Invalidate a reviewed scope, do not alter user data/passwords/session markers. No transition SQL/migration is executed or authorized here.

No structural migration is inherently required for UTC-DATETIME B/C, **but an explicit reviewed data transition is required**. Proposal approval must specify exact invalidation scope, write freeze/rolling-release strategy, retry UX, known clock skew tolerance, monitoring and rollback behavior. OptionC epoch columns would instead require a separately reviewed migration, dual-read/write rules, and schema rollback plan.

### Security, races, operational verification and rollback

Preserve uid/action binding, hashes, real CSRF/rate limits, mail failure/error contracts and pending-login/signup gates. Current regeneration update+insert and verification SELECT+UPDATE are not atomic single-use claims. An atomic-consumption redesign requires its own bounded review and competing-connection tests; do not assert that fixing time fixes races.

Before rollout, validate generation+verification/cleanup across mismatches and timezone changes using exact candidate; report now/UTC/epoch/zone metadata without OTPs, tokens, cookies or identities. Monitor aggregate issuance/rejection/expiry/cleanup counts and clock drift, not secrets. Test DB errors and existing delivery/invalidation behavior. Confirm FPM/CLI/long-running reconnect timezone policy. Never expose debug codes.

Rollback before merge is simply keep draft unmerged. Test/proposal changes can be reverted to accepted Phase3Y without application/schema rollback. For a separately approved UTC writer correction, reverting old code against new UTC rows can reintroduce invalid timing: coordinate writer pause and reviewed invalidation/version handling again. Rollback must not resurrect used or invalidated codes. There is no safe automatic reinterpretation of naive historic rows.

**Decision gate:** obtain separate review and explicit authorization of this exact UTC-DATETIME behavior, affected file, transition/invalidation choice, availability impact and operational checks before implementing it. Marker TTL/equality semantics and cross-session consumption concurrency are separate decisions. This PR contains tests and this proposal only.
