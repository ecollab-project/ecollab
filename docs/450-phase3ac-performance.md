## C: durable single winner

verify rejects caller-owned PDO transactions and session autocommit=0 without committing caller work. It selects the eligible row and checks bcrypt without holding a lock. It then begins its own transaction, acquires that selected row by id FOR UPDATE, and starts a separate conditional UPDATE. That UPDATE rechecks id/user/action/unused/strict UTC expiry. Only rowCount===1 followed by a successful commit returns success to AuthService, which can subsequently mint a reset token. Losers return the existing expired/not-found response. No silent retry or unconsume occurs; DB errors throw to existing API handling. A later caller rollback cannot restore the committed code.

The extra lock statement is deliberate: MariaDB NOW/UTC_TIMESTAMP are statement-start clocks. Evaluating expiry in an UPDATE that spends time waiting for a lock can use stale time. Acquiring the lock first and starting the eligibility UPDATE afterward handles that wait. Locks are not held during bcrypt.

Contract: at most one successful consumption and reset-token issuance per stored OTP row. It is not exactly-once successful token delivery across crashes. If the process or caller fails after commit, the code stays consumed and a fresh request is required. A lost connection or ambiguous commit is failure, never permission to issue a token or retry. Connection-loss evidence records PDO's stale transaction flag on the disconnected socket; no token or success escapes. Supported DB setup uses exceptions and InnoDB. Actual production transaction/storage/durability settings were not inspected.

## B: isolated legacy rehearsal, retention and rollback

`tests/phase3ac-transition.php` is guarded by the existing owned-runtime bootstrap and owned synthetic actor check. It is not a production transition utility. It constructs deliberately ambiguous legacy unused rows and a used row with inconsistent unknown timestamps. Existing used rows are byte-for-byte identical before/after; no timestamp interpretation, conversion or history deletion occurs. All old actions become ineligible, fresh issuance/verification works, and rollback never clears used_at.

Production transition remains NOT RUN and unauthorized. A deployable cutover requires pausing every issuer/verifier and cleanup, draining in-flight calls, inventorying external writers/triggers/events, protecting retained history, invalidating every legacy unused row regardless of apparent expiry, and switching all supported writers/readers together. Do not rely on waiting 600 seconds. Do not restart old writers beside UTC writers. Existing authenticated sessions, PHP reset tokens and signup markers are unchanged.

**Retention gate:** existing unknown-provenance used rows cannot safely be interpreted by UTC cleanup. No production purge is approved until that history has been preserved in an access-controlled, integrity-verified archive under a reviewed retention plan. The rehearsal does not call purge on legacy history. There is no existing application caller/scheduler for purgeExpired in inspected tracked source; the method itself retains the original 24-hour strict cleanup policy using UTC for UTC-origin rows. External cleanup jobs and actual archival storage/access/retention must be resolved before rollout; no archive/schema migration or production export was implemented.

Recovery is forward-only after invalidation. Keep OTP traffic paused on an incomplete transition. Never restore old unused rows, clear used_at, or restore a pre-consumption snapshot into the active store. Prefer roll-forward. Rolling code back requires stopped issuance and a separately reviewed fresh transition; simply reverting code while UTC rows remain would reintroduce incompatibility. Before any transition, reverting this isolated patch to the exact base requires no schema rollback, but restores both known defects and cannot be called a security-safe baseline.
